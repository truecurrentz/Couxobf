# Against a review of the architecture

A reviewer with a virtualization-obfuscation background scored this tool in
twenty-nine points, ending with the verdict that the weakness is not a too-simple
VM but a *reusable* one:

> Once I mapped the VM handler semantics in your sample, the same mapping would
> likely apply to another script generated by the same compiler version.

This document is the response: which of those points were true, which had already
been fixed, which are fixed now, and which we are deliberately not doing. Nothing
here is a promise; each row either names the code and test that satisfies it or
says the capability does not exist.

**Verdicts.** ✅ already done when the review was written · ⭐ implemented while
answering it · 🔶 partial, gap named · ⬜ not built · 🚫 will not build, reason
given.

## The twenty-nine points

| # | Point | | Response |
| --- | --- | :- | --- |
| 1 | Encryption is not the primary protection; keys and ciphertext ship together | ✅ | The whole of `docs/SECURITY.md` says this ("Client-side obfuscation is not irreversible... it raises cost; it does not prevent"), and the report repeats it inside the artifact. Server authority is named as where secrets belong. |
| 2 | Make every build's VM different, not just the numbering: different handler layout too | ⭐ | Per group: family, dispatcher shape, opcode numbering, instruction format, ISA subset, opcode cipher, and now the order the arms are tested in (`arm_seed` in `FormatSpec`, applied in `dispatch_entries`). Handler *bodies* are still one implementation each — see 🚫 at #24. |
| 3 | Small VM variants; a function gets only the instruction families it needs | ⭐ | `Config.vm_isa_subset` → `encode.required_ops(proto, fmt)` unioned per group → `OpcodeMap.shuffled(ops=subset)`. Measured on a four-function program at `vm_variety=3`: groups carry **19, 10 and 7** handlers instead of 43. On the pinned example command (`maze.luau`, seed `0xC0FFEE`, one flag of difference) the artifact goes 90,523 → **67,411 B, −25.5%**, with per-group dispatch numbers 107/103 → 67/31 — smaller and less transferable at once. |
| 4 | Virtualize selectively; do not VM glue code | ✅ | The classifier (`couxobf/classify.py`) plus node floors per level; the report lists every prototype left native *with its reason*. |
| 5 | Split one sensitive function across several VM domains | ⬜ | Groups partition prototypes, so one function runs on one interpreter. Doing it properly means moving a live frame (registers, pc, open upvalues, yield state) between two interpreters mid-function; the correctness cost is total and the protection gain is a smaller number than #3's. Not built, not refused — it is the next structural item after #18/#19 below. |
| 6 | Do not leave the dispatcher visually obvious | ⭐ | Three shapes (`nested_if`, `decision_tree`, `bucket`), drawn per group; arms permuted; the fetch no longer reads `byte(code, pc)` at the dispatch site. |
| 7 | Mix dispatch styles across functions | ✅ | `dispatcher_family="mixed"` plus `dispatcher_splitting` per group, with the pinned shape honoured for group 0 (`_dispatcher_rotation`). |
| 8 | Separate fetch, decode and execute | ⭐ | `local op = _ro(pc)`: the fetch is a generated reader (`reader_source`), the decode is the cipher's inverse, and the handlers see only a dispatcher number. One reader per group, so three interpreters have three different fetches. |
| 9 | Randomize instruction layouts per build | ✅ | `op_bytes`/`reg_bytes`/`wide_bytes`/`pad`/`wides_first`/masks per group: 12 distinct field layouts across 6 seeds, all four jump-target modes. |
| 10 | Separate opcode identity from handler identity | ⭐ | That is `Config.opcode_cipher`: the stream carries a bijective image (rotation, affine, halves-swap) of the number the dispatcher branches on, so `encoded opcode → decode → handler` exists as a layer instead of being an identity. Costs no bytes. `tools/reuse-audit.py` scores what it buys (below). |
| 11 | Several encodings for the same operation | 🔶 | One operation can be reached by several *numbers* (`opcode_aliases`), by a fused pair (`instruction_fusion` + `super_instructions`), and under several *layouts* (per-group formats). What it is not: `ADD r1,r2,r3` rewritten as `MOVE tmp,r2; ADD r1,tmp,r3`. See 🚫 at #15 — an equivalent-form pass at the IR level changes what a profiler and an error message see, and the versions that do not are foldable noise. |
| 12 | Fuse common sequences, generated per function not from a fixed list | ⭐ | `FUSABLE` pairs are the universe, but each build's format draws a subset (`rng.sample`), the group's numbering decides which pairs actually fit (`allocated_fused`), and the report prints the count for each group (`16 fused` and `10 fused` in the pinned example; a group whose numbering fits no pair prints none, which is the honest outcome rather than a failure). |
| 13 | Basic-block diversification: splitting, merging, selective flattening | 🔶 | Permutation of block layout (`couxobf/vm/layout.py`, with the `JMP` insertion that a permutation requires) and within-block instruction reorder where the format permits. No splitting or merging: those need liveness re-derived per shape, and the lowerer cannot currently provide live-range splitting (the same missing prerequisite that keeps a full register permutation off the table — see `Config.register_randomization`). |
| 14 | Opaque predicates, if used, must resist constant folding | 🚫 | `opaque_predicates` is declared and reported pending. A predicate we can prove at build time is provable by any folding pass that reads the same program; one we cannot prove is a branch whose dead side may execute. Both are noise. The honest version is #12 and #3: real semantic variety, not arithmetic camouflage. |
| 15 | Do not ship meaningless arithmetic garbage | ✅ | Agreed and enforced: `junk_level` is declared and reported pending; decoy *values* in the pool are the only padding built (technique #14) because a pool entry is data the program never reads rather than a branch it might take; and the size budget's trim ladder (`pipeline._BUDGET_TRIMS`) gives up decoys, aliases and padding before it gives up any structural transform, which is the project stating in code what it thinks noise is worth. |
| 16 | Derive transformations from the build seed, function hash and structure | ⭐ | The seed fans out through domain-separated streams (pool, VM, strings, cfg, names, constants), so unrelated layers do not correlate; the ISA subset is derived from *the function's own instructions*, which is the "function hash" input this point asks for. Not from runtime randomness, deliberately: reproducibility is a feature (`reproducible_seed` reproduces byte for byte, and 6 seeds produce 6 distinct artifacts). |
| 17 | Diversify the string system: page size, index form, chunking, decode order, layout, implementation | 🔶 | Levels 0–3; shuffled page order; per-occurrence tickets instead of ids; page contents encrypted with their own key material. Not: page size (512 bytes, fixed -- a constructor argument of `StringBank` constrained to multiples of 64 and deliberately not a `Config` field, because a knob nothing can set is worse than no knob), decode order, or more than one implementation of the reader. |
| 18 | Do not put all strings in one central bank | 🔶 | Strings live in their own bank, separate from the constant pool, and each page is independently keyed; but there is one bank per artifact, so one recovered reader covers it. Per-group banks are the same change as #19 and the next one on the list. |
| 19 | Split important constants into several pools | ⬜ | One pool per artifact, authenticated as a whole, with 24 planted decoys in a maximum build. The change is to give each VM group its own pool with its own key and its own AAD binding to that group's format — which is a real reduction in single-point extraction and also what makes #5 possible later. |
| 20 | Do not treat anti-tamper as prevention | ✅ | `guard.py`'s own docstring and `docs/SECURITY.md` both say the guard is *detection* that raises cost; `guard_policy=fail` refuses rather than pretending to protect, and the report prints what it captured and whether it tripped. |
| 21 | Keep the authenticated-encryption structure; fix key placement instead | ✅ | Tag-before-decrypt, AAD over nonce/lengths/context, one AEAD per blob, published test vectors for the primitives. `KeyMaterial.from_seed` needs ≥16 bytes and refuses less, so a short seed is a build error rather than a weaker key. |
| 22 | Do not invent more cryptography | 🚫 | Agreed with the reviewer. There is no new primitive here: ChaCha20 + HMAC-SHA-256 + HKDF-SHA256, cross-checked against Python's `hashlib`/`hmac` in both directions (`tests/test_luau_crypto.py`). If a future change needs crypto, it goes through the same "standard primitive, published vectors" rule. |
| 23 | Authenticated build identity | ⭐ | `structural_fingerprint(plan)` digests each group's family, dispatcher, **opcode count** and format — so the new ISA subset participates in it — and is folded into the pool's AAD. A pool from one build does not open in another. Reported, and bound only when a VM actually runs (see the checklist's #39). |
| 24 | Semantic-equivalence regression tests over the hazard list | ✅ | `tests/fixtures/micro/*.luau`: 40 fixtures, each one semantic hazard — nil, booleans, NaN and infinities, signed zero, tables, metatables, closures, upvalues, varargs, multiple returns, iterators, `pcall` error text, per-iteration capture, numeric-for coercion — run differentially under the pinned toolchain. What the list does not cover is coroutines and yield: `coroutine` exists in this tool only as a name in the globals whitelist in `sema.py`, is not VM-supported, and has no test -- the technique checklist scores that gap at its own #58 rather than folding it in here. |
| 25 | Differential-test every VM instruction | 🔶 | Every opcode in `isa.SUPPORTED` is asserted to appear in the corpus (`test_vm.py` fails listing the uncovered ones), and per-opcode static invariants run for each (pc advance, operand size, declared-name hygiene, jump geometry). What is missing is per-opcode *randomized* differential cases — generating argument shapes per op rather than relying on the hand-written fixtures to have covered them. |
| 26 | Measure obfuscation instead of judging size | ⭐ | `tools/reuse-audit.py` measures knowledge transfer between builds (below), and it runs inside the suite (`tests/test_reuse.py`) with a positive control so a metric that measured nothing would fail. The cost report already gives per-build sizes, counts, handler numbers and elapsed time; runtime overhead is measured for VM dispatch (~10× on 400k instructions) and not per technique. |
| 27 | Build an attacker-model suite over the eight analysis classes | 🔶 | A (static strings): 0 of 9 source literals present in a maximum build. B (constant recovery): requires the key that is in the file, and a bit flip stops the runtime. C (opcode identification): measured, see below. D (CFG reconstruction): not measured. E (symbolic execution) and F (dynamic tracing): mitigated (handler bodies are plain Luau; the fetch is generated) but not measured. G (runtime dumping): the guard observes and can refuse. H (cross-build reuse): measured. |
| 28 | Cross-build diversity is the main objective | ⭐ | It is now the thing with a number attached, and the number is what the review said it should be: see the table below. |
| 29 | Rating: diversity 3/10, VM semantic diversity 3/10, dynamic scheduling 2/10, key isolation 2/10 | 🔶 | Diversity and semantic variety are measurably higher now (see #2/#3/#10 and the audit). Dynamic scheduling is still 2/10 — nothing reschedules at run time, and #5 is where that would come from. Key isolation is still 2/10 for the reason in #19: one key, one pool, in the same file. Those two are the honest remaining low scores. |

## What the audit measures, and what it found

`python3 tools/reuse-audit.py examples/maze.luau --seeds 3` builds the same program under four configurations, learns a "value means operation" table from
each build by sweeping its payload the way a static tool would, and scores that
table against the truth of every other build. The middle row is the interesting
one: it separates "the numbers moved" from "the bytes stopped meaning anything".

```
config       instrs  numbering   payload    shape    arms    isa
----------------------------------------------------------------
stable          111      100%      100%     100%    100%   100%
numbered        111        1%        0%     100%    100%   100%
hardened        111       12%        1%       0%      0%   100%
polymorphic     111        6%        1%       0%      0%   100%

stable     handlers per VM, per build: [[43], [43], [43]]
numbered   handlers per VM, per build: [[43], [43], [43]]
hardened   handlers per VM, per build: [[22], [22], [22]]
polymorphic handlers per VM, per build: [[18, 6, 12], [18, 6, 12], [18, 6, 12]]
```

`stable` is the positive control: a protector that varies nothing transfers
perfectly, which is what makes the other rows mean something. `numbered` is the
reviewer's complaint answered at the cheapest level — shuffling numbering already
takes payload transfer to 0% — while `shape` and `arms` stay at 100%, because with
`operand_randomization=False` every build has the same format and the same handler
order. `hardened` is where the format, the cipher, the arm permutation and the ISA
subset all move, so nothing transfers except the *sizes*: `isa` stays at 100%
because how many handlers a function needs is a property of its code, not a
secret. `polymorphic` is `vm_variety=3`: three interpreters per artifact, carrying
18, 6 and 12 handlers here -- 19, 10 and 7 in the suite's own four-function program -- and a matcher holding one table has three interpreters to feed it into.

What the audit does **not** claim: that 1% transfer is a bound. It models one weak
matcher over straight-line sweeps. A tool that reads the emitted interpreter
instead of the payload recovers a correct table for whatever build it is pointed
at, and then has to redo the format per build — which is why `shape` and `arms`
are in the table rather than just `payload`.

## Deliberately not done

Four of the reviewer's suggestions and framings would make this tool worse at its
own job, and the reasons are worth writing down:

- **Arithmetic noise and opaque predicates** (#11's rewrite temptation, #14). A
  build-time-provable predicate is foldable by anything that reads the program; a
  build-time-unprovable one has a dead side that may run. Both add bytes and
  subtract legibility from *correctness*, which is the one thing here that is not
  negotiable.
- **More cryptography** (#22). The primitives are standard, vector-tested and
  cross-checked between Python and generated Luau. Custom primitives would add
  bugs and no measured cost to an adversary.
- **Anti-tamper framed as prevention** (#20). The guard is detection with three
  levels and an explicit policy, and it says in the report which of the two it did.
- **Runtime randomness for diversity** (#16's last clause). Reproducibility is a
  product feature: the same source, seed and version produce a byte-identical
  artifact, which is what lets a build be reviewed, diffed and re-verified later.

## Next, in order

1. **Per-group constant pools** (#18, #19). One pool per VM group, each keyed and
   AAD-bound to that group's format, so no single accessor yields the program's
   data. This is the change that reduces the payoff of one extraction routine, and
   it makes #5's cross-domain frame handoff expressible.
2. **Block splitting** (#13), once the lowerer can hand `layout` live ranges.
3. **Per-opcode randomized differential cases** (#25), so the instruction set can
   grow without correctness resting on which fixtures happen to exist.
4. **Chunked pool with per-chunk keys** (technique #41), which the string bank's
   page structure already proves out.
5. **A second, stronger matcher in the audit** (#27's E/F/G classes), because the
   only thing worse than a measured 1% is an unmeasured 0%.
